# AGENTS.md

## Project Shape
- `backend/` is a Django 4.2 + DRF API service; entrypoints are `backend/manage.py`, `backend/config/settings.py`, and `backend/config/urls.py`.
- `frontend/` is a Vue 3 + Vite + Element Plus app; entrypoints are `frontend/src/main.js` and `frontend/src/router/index.js`.
- Backend API prefixes are mounted in `backend/config/urls.py`: `/api/users/`, `/api/proxy/`, `/api/dashboard/`, `/api/models/`, `/api/tickets/`, and `/api/image-gen/`.
- Frontend routes use `/app` for user pages and `/admin` for the Vue admin UI; Django admin is also `/admin/` on the backend server, not through the Vite proxy.

## Commands
- Backend setup/run from `backend/`: `pip install -r requirements.txt`, then `python manage.py migrate`, then `python manage.py runserver`.
- Create migrations only when model changes require them: `python manage.py makemigrations`, then run `python manage.py migrate`.
- Frontend setup/run/build from `frontend/`: `npm install`, `npm run dev`, `npm run build`, `npm run preview`.
- `npm run build` runs `vite build && node scripts/zip-dist.js`, so it creates both `frontend/dist/` and `frontend/dist.zip`. There is **no** separate `build:zip` script — the root README used to tell you to run one, and the only thing that produced was `Missing script: "build:zip"`.
- There are no configured frontend lint/test/typecheck scripts; use `npm run build` as the frontend smoke check.
- Backend unit tests are **pure Python**: they need neither a database nor Django settings. Run every one of them from `backend/` with `python run_tests.py`. **That run's output is the authoritative package list** — the runner derives it from `apps/*/tests/` and prints each package with its case count; do not copy the list into this file. (This bullet used to enumerate the packages, and it was already missing `apps/ai_models/tests/` — exactly the drift the next bullet forbids.) What the packages cover, by topic: OpenAI↔Anthropic adapters and streaming state machines (`api_proxy`), balance runway (`dashboard`), the repo-level contracts verified by reading files rather than calling code — docs, env vars, the frontend lockfile (`docs`), image pricing and billing-path invariants (`image_gen`), upstream models (`ai_models`), and upstream usage parsing / billing result vocabulary / user-facing copy / amount formatting / unbilled-stream detection (`utils`), and the invite-reward decision — `apps/users/invite_reward.py` is pure and takes its two queries as callables, so `every` and a zero amount issue none (`users`). The run also prints **every app that has no tests at all**, and fails outright if such an app is not declared in `run_tests.py`'s `NO_TESTS_YET` table — so adding an app without deciding about its tests is loud instead of silent. The declared apps are printed by the run; don't list them here either.
- Docs are checked too. `apps/docs/tests/test_docs_contract.py` fails when a doc tells you to run a command that does not exist, or states a database requirement other than the one `settings.py` actually connects to. The runtime database has exactly one home: `REQUIRED_DATABASE` in `backend/config/settings.py` (`MySQL 5.7+`, which is what the deliberate `check_database_version_supported` bypass implies). Four docs used to give three different answers — the root README's env-requirements list even named a database the code does not use, while its own tech-stack table named MySQL — so anyone self-hosting installed the wrong thing. What counts as a defect is narrow on purpose, and both narrowings came from false positives hit while writing the check: a command counts only inside **executable context** (fenced blocks, list items, table rows), because a sentence explaining that a script never existed necessarily contains that script's name; and a database requirement counts only as **product + version** (`MySQL 5.7+`), because AGENTS.md is written entirely in bullets and so a note recording "a doc once named the wrong database" cannot be scoped away by context alone. The real defects all carried a version number. Cost, stated plainly: a versionless requirement like "you need PostgreSQL" would slip through — accepted, because a check that fires on history-recording gets routed around once and then switched off. Command **forms** got the same treatment: `npm run` was checked from the start, but `pnpm <script>` and `node <file>.js` — both of which the docs actually use — had no landing point at all, so a doc could hand you a script that does not exist as long as it was spelled with the other package manager. All four forms are now checked (pnpm against `package.json` scripts, minus the built-in subcommands listed in `PNPM_BUILTINS`; `node` paths resolved against `frontend/` as well as the repo root), and the *list of forms* is reconciled against the docs: every tool name appearing at the start of a line inside a **`bash`-tagged fence** must either have a check or be declared in `UNCHECKED_COMMANDS` with a reason — a table that is verified in both directions, so a new tool (`docker`, `yarn`, `bun`) is loud instead of silently unmanaged. Two deliberate narrowings: only shell-tagged fences are scanned (other fences hold Vue/JS snippets whose first token is `title:` or `useSeoMeta(`), so tag your command blocks `bash`; and the alignment stops at the tool name, since arguments vary too much to align.
- `run_tests.py` scans `apps/*/tests/` instead of a hard-coded list, and **fails** if a `tests/` directory lacks `__init__.py` — unittest would otherwise skip it silently. Never enumerate test packages by hand in docs or scripts: `apps/dashboard/` has no `__init__.py`, so `python -m unittest discover -s apps -t .` skipped that whole package **without any error** while the docs claimed it ran. That rule now has a landing place: `apps/docs/tests/test_docs_contract.py` fails if any doc hands you a narrowing `unittest discover` command **inside a fenced block** — `backend/README.md` used to hand you two of them (116 + 21 cases, against the runner's 314), and all three printed the same `OK`. The narrowing to fenced blocks is deliberate: this file is written entirely in bullets and necessarily names that historical command, so a list-item-wide check would fire on its own history. The same file also checks the README's project-structure tree against `backend/apps/` in both directions — the tree listed 7 of the 8 apps (`apps/docs/`, where that check lives, was the missing one).
- Environment variables are checked in **both** directions by `apps/docs/tests/test_env_contract.py`: every variable declared in `backend/.env.example` must be read by backend code, and every variable `config/settings.py` reads must be declared there. `frontend/.env.{development,production}` and `frontend/src/**` are held to the same rule, and the README's env table may only list variables the template actually has. The template used to declare `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` while the code only read `REDIS_URL` — so `backend/.env` was copied and filled in with a real host and password that did **nothing at all**, and the app silently fell back to `settings.py`'s `redis://127.0.0.1:6379/1`: a different Redis, no password, not one error line. Two narrowings, both deliberate: comment lines are not declarations (a note recording the variables that were removed necessarily names them), and `*.d.ts` is not a reader (`vite-env.d.ts` declaring `readonly VITE_X: string` is exactly what made two unused variables look alive). There is no allow-list — to keep a variable "for later", give it a read site.
- Streaming bytes must be decoded through `IncrementalUtf8Decoder`, never `chunk.decode('utf-8', errors='replace')`. A TCP/HTTP fragment can split a multi-byte character; single-shot decoding replaces it with U+FFFD, turning one Chinese character into three `�` — permanently, and the upstream data was fine. The same helper is used by the usage-parsing buffers in `views_openai.py` / `views_responses.py`.
- Billing invariants, all three must stay green: every deduction happens inside `transaction.atomic()` **and** behind `select_for_update()`, with the balance re-read under the lock (`views_openai.calculate_and_deduct_cost` and `image_gen.views._deduct_cost` are two implementations of one thing — fix both). Image generation deducts **before** persisting `GeneratedImage` rows; the reverse order lets a request that fails on insufficient balance leave downloadable images behind. Because of that order, a failure while saving the image must be refunded (`image_gen.views._refund_cost`): credit the balance back, write a `type='refund'` `Bill`, and zero that generation's `cost` as the idempotency marker. The refund takes the same locks in the same order as the deduction (`User` before `ImageGeneration`) — the reverse order lets a concurrent deduct and refund wait on each other. A refund failure is logged and surfaced to the user, never raised: it would hide the original error.
- Invite rewards are a money path too, and are held to the same standard as the deduction paths above. The judgement — whether to pay, how much, and whether it goes to manual review — lives only in `apps/users/invite_reward.py` (pure Python, no Django import; the two queries arrive as callables, so `every` and a zero amount issue **none**). Amounts are quantised to 2 places, matching `InviteReward.reward_amount` / `recharge_amount`, so any reward record can be recomputed from its own two fields; a reward that quantises to 0 is not written at all; and the review threshold is compared against the quantised amount — comparing the raw product let a `99.999` reward skip review *and* credit a number the record did not show. Both crediting entry points — `apps/users/utils.py::process_invite_reward` and `apps/dashboard/views.py::approve_reward` — take the inviter's `select_for_update()` **before** they read, and approve re-checks `status='pending'` under that lock; without them two recharges both count as a first reward, and two admins both credit the same one. `apps/users/tests/test_invite_reward.py` reads both functions' source (comments and docstrings stripped, so a comment claiming a lock cannot pass) to keep the lock ordering, and each of those assertions is paired with a reverse control so it cannot pass by never firing.
- **Both** deduction functions return `(cost, DEDUCT_OK | DEDUCT_INSUFFICIENT | DEDUCT_ERROR)`, never a boolean. A server-side failure (DB read/write blew up) must never be reported as "insufficient balance" — that nudges the user to top up and dresses a 500 up as a 400. Note the asymmetry, it is deliberate: `image_gen._deduct_cost` can return `DEDUCT_INSUFFICIENT`, while `calculate_and_deduct_cost` (the LLM path, used by both `/v1/chat/completions` and `/v1/responses`) **never** does — it allows the balance to go negative so a request that already consumed upstream cost still gets billed, and the overdraft is stopped by the `balance <= 0` gate at each entry. So on the LLM path every deduction failure is a server-side failure.
- User-facing billing copy is reached through `apps/utils/billing.py` only: entry checks call `precheck_failure(balance)`, deduction failures call `deduct_failure_payload(status, cost, balance)` (OpenAI-compatible endpoints) or `deduct_failure(status, cost, balance)` (image endpoint); the error envelope for billing is `openai_error(message, code)`. `apps/image_gen/tests/test_billing_path.py` enforces this by reading the source — a literal "insufficient balance" string anywhere in `views_openai.py` / `views_responses.py` code (comments, docstrings and log calls excluded) turns it red. A failed deduction reports 500 and never mentions the balance; only the entry gate (which checks `balance <= 0`, a fact) says "余额不足".
- Money and identifier rules have exactly one home: image pricing (including the fallback unit price used when `per_image_price = 0`, which means "unset", not "free") lives in `apps/image_gen/pricing.py`; the billing result vocabulary, user-facing copy, amount formatting and the HTTP status / `code` mapping live in `apps/utils/billing.py` (pure Python, no Django import — `apps/utils/__init__.py` therefore re-exports nothing, so `from apps.utils import billing` stays importable without Django); the `chatcmpl…` → `resp…` id mapping lives in `apps/api_proxy/adapters/ids.py` and is imported by both the streaming and the non-streaming adapter. Do not add a second copy under `views.py` / `response_adapter.py` / `streaming_adapter.py`. Reading **usage** out of an upstream response is single-sourced too: `parse_usage_dict` / `parse_usage` in `apps/utils/billing.py` are the only place that knows the three protocol shapes (`prompt_tokens` / `completion_tokens`, the Responses API's `input_tokens` / `output_tokens`, Anthropic's `cache_read_input_tokens`) and the cache-hit field. It had **four** copies until the ninth round and they disagreed about which fields they recognised, so the same upstream could report different token counts — and therefore a different charge — depending on the endpoint. Both endpoints settle through `views_openai.update_usage_log` (which writes all four token fields, `cached_tokens` included) and `apps/api_proxy/tests/test_usage_single_source.py` reads the source to keep it that way.
- Streaming request bodies are built only by `apps/api_proxy/adapters/upstream_body.py` (`build_stream_body`), which forces `stream_options.include_usage = true` for the OpenAI protocol. An OpenAI-compatible stream carries **no `usage` chunk at all** unless the request opts in, and the settle step is guarded by `if total_tokens > 0` — so without that flag the deduction is skipped outright: balance untouched, usage logged as 0, no bill, no error, indistinguishable from a genuinely free call. Anthropic streams deliver usage in `message_start` / `message_delta` and reject `stream_options`, so the flag is added for the OpenAI protocol only. Because of that failure mode, each streaming settle path calls `billing.unbilled_stream_note()` — a successful stream with zero tokens logs a WARNING instead of passing silently. `apps/api_proxy/tests/test_stream_body.py` pins both the behaviour and the structure (both endpoints must route through the helper; no `body['stream'] = …` in the views).
- For backend smoke checks beyond the unit tests: `python manage.py check`.

## Environment
- Backend reads `.env` via `python-dotenv`; start from `backend/.env.example` and provide MySQL settings plus optional Redis as a single **`REDIS_URL`** with the password embedded in the URL (`redis://:password@host:6379/1`) — separate host/port/password variables are read by nothing.
- Django settings use MySQL by default and intentionally bypass Django's MySQL version support check for MySQL 5.7 compatibility.
- Frontend API base is `VITE_API_BASE_URL` and defaults to `/api`; `frontend/.env.development` and `.env.production` both set `/api`.
- Vite dev/preview proxy only forwards `/api` to `http://127.0.0.1:8000`; do not add `/admin` proxy unless deliberately replacing the Vue admin route.

## Backend Notes
- `AUTH_USER_MODEL` is `users.User`; authentication uses `apps.users.authentication.JWTAuthentication` and the `EmailOrUsernameBackend`.
- API responses use the repo's unified `{code, msg, data}` shape from `apps.utils.response.APIResponse`; frontend Axios unwraps that format in `frontend/src/stores/index.js`. This used to read "commonly use", and that hedge was load-bearing: `apps/users/views_usage_log.py::APIAccessLogViewSet` never overrode `list()`, so `/api/users/usage-logs/` served a bare array with no `total` and no `page_size` cap while the frontend guessed with `res.results || res || []`. The only deliberate exception is the OpenAI/Anthropic-compatible surface under `/api/proxy/v1/...`, which must return the upstream protocol shape verbatim. Everything else — list endpoints included — goes through the envelope, and **paginated lists go through `apps.utils.pagination.paginate()`** (one shape: `{results, total, page, page_size}`); `apps/utils/tests/test_pagination.py` checks both directions, so a module that hands pagination back to a hand-rolled copy fails the suite. The same bare-array hole existed on `/api/models/upstream-accounts/` (`UpstreamAccountViewSet` had no `list()` either) — worth remembering that "which viewsets never override `list()`" is a question grep answers, not one you should assume. On the client side, `page_size` is capped at `MAX_PAGE_SIZE` = 100, so "I want everything" must be expressed by paging, never by a bigger number: use `fetchAllPages()` from `frontend/src/utils/pagination.ts` (it returns `truncated`, and every call site has to surface that). `apps/utils/tests/test_frontend_pagination_contract.py` enforces the pairing statically, and actually executes `pagination.ts` under `node --experimental-strip-types` to prove the paging loop terminates.
- OpenAI-compatible proxy routes live under `/api/proxy/v1/...`; unsupported `/v1/*` paths fall through to `ModelsView`.
- The proxy supports OpenAI and Anthropic protocol adaptation in `backend/apps/api_proxy/adapters/`; preserve request/stream/response conversion behavior when touching proxy code.
- Image generation stores generated files under Django `MEDIA_ROOT` and has a cleanup command: `python manage.py cleanup_images`.

## Dependency And Artifact Gotchas
- `frontend/package.json` has npm scripts, but the only **tracked** lockfile is `frontend/pnpm-lock.yaml`; `package-lock.json` does not exist in the repo and is gitignored by the root `.gitignore`. So the documented `npm install` neither reads nor updates the tracked lockfile — after changing a dependency, run `pnpm install` in `frontend/` to bring `pnpm-lock.yaml` back in step. That agreement used to rest on a "verified: its specifiers match `package.json` today" note, which is the kind of sentence that expires in silence; it now has a landing place: `apps/docs/tests/test_lockfile_contract.py` compares `importers['.']` against `package.json` in **both** directions — package-name sets *and* specifier values — across `dependencies` / `devDependencies` / `optionalDependencies`. So a dependency bump followed by the documented `npm install` fails the suite instead of quietly leaving the tracked lockfile stale. Deliberate non-goals: the `version:` lines (a resolution result, not a contract — it moves with the registry), `peerDependencies` (pnpm's importer section does not record it, and nothing declares one today; re-check pnpm's behaviour before adding one), and there is no allow-list — a package appears on both sides or on neither. The check parses the lockfile with the standard library only (fixed indentation, three levels); both the hand-written minimal fixture and a second, independently written indent-tree parser were used to confirm the parser is reading what it claims to read.
- Root `.gitignore` ignores `frontend/package-lock.json`, generated frontend declaration files, `dist/`, `dist.zip`, `.env`, logs, and Django media.
